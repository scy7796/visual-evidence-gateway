# 宣传口径与优化复审

这份文件回答两个问题：首发时什么值得放在首页，以及哪些话必须等真实机器结果后再说。

## 核心定位

最强且成立的定位不是“又一个视觉模型封装”，而是：

> **不给主代理换脑，只给它接一条受控的 Luna 视觉证据链。**

DeepSeek、OpenCode 或其他文本代理继续负责规划、编码和长上下文；只有当答案依赖像素时，才通过一个只读 MCP 工具委派给 Luna。返回的是可验证的简短证据，不是把整张图、完整 OCR 和视觉推理长期灌进主代理上下文。

## A 级：适合首页重点宣传

| 卖点 | 推荐表述 | 为什么成立 | 证据状态 |
|---|---|---|---|
| 保留主代理 | 让 DeepSeek/OpenCode 保持主控，只在需要像素证据时调用 Luna | MCP 把视觉职责与规划/编码职责分离 | 本地代码与契约已验证 |
| 受控视觉证据链 | 一个只读工具统一完成路径授权、图片处理、结构化证据和最终校验 | 不是单纯把图片转发给模型 | 本地代码、测试、审计已验证 |
| 最小上下文 | 默认只返回答案、定位证据、相关文字和不确定性 | reducer、严格 Schema 和输出预算共同约束 | 本地测试已验证 |
| 不静默漂移计费路径 | 默认要求 ChatGPT 登录，移除 API 计费变量；Luna 不可用时失败 | 避免“配置写订阅，实际走 API” | 命令构造与回归测试已验证；账号侧需真实探针 |
| 安装即验收 | 一键流程不是安装完就成功，而是必须通过登录、连通性和真实随机像素探针 | 能发现“装上了但根本看不了图” | 安装器契约已验证；跨平台需实机 |
| 失败关闭 | 模型身份、Schema、语义充分性或注入终检失败时不返回伪证据 | 失败可见优于未知模型静默顶替 | 本地测试已验证 |

## B 级：适合技术页或发布说明

| 卖点 | 准确表述 | 注意事项 |
|---|---|---|
| 自适应图像处理 | 内置稳定读取、受控暂存、裁剪、长图分块和失败重试 | 可以宣传“具备机制”，不能在没有消融实验时宣传“成功率提升 X%” |
| 图片提示注入收敛 | 图片文字被视为不可信内容；Codex 子进程关闭 shell、子代理、hooks、远程插件和网页搜索，结果还要经过注入终检 | 不应写成“绝对防注入”或“完全沙箱” |
| 文件安全 | 授权根目录、symlink/junction/reparse、TOCTOU、像素炸弹和异常文件防护 | 适合安全模型章节，不必挤占首页 |
| 隐私默认值 | 默认不保存原始提供商响应、完整 OCR，也不向宿主返回绝对缓存路径 | 仍需说明图片会发送给配置的远程视觉后端 |
| 签名缓存 | 缓存绑定实际发送字节和结果相关配置，命中时后端调用数为 0 | 不宣传“本地快很多”；主要价值是避免重复远程调用 |
| 单工具接口 | 对宿主只暴露 `vision.inspect`，降低工具选择和权限面 | 简单是优势，但不是视觉质量证据 |
| 快速本地反馈 | 参考构建机的本地编排低于 100 ms，完整回归约数秒 | 必须附环境和范围，不能写成真实 Luna 延迟 |

## C 级：真实验收通过后才能加到发布页

- 当前账号通过 ChatGPT/Codex 订阅实际可调用 `gpt-5.6-luna`；
- 真实端到端延迟的 median、p95、min、max；
- Windows、macOS、Linux 一键安装结果；
- Codex、OpenCode/DeepSeek 等实际宿主都能发现并调用；
- 同一图片重复调用确实不再请求 Luna，并量化节省时间；
- 长图、小字号的裁剪/分块相对关闭重试的成功率增益；
- 与 Codex 原生附图在同一账号、同一图片、同一 Luna 配置下的正确率、延迟和输出长度；
- 主代理上下文或 token 的实际节省量；
- 提示注入测试集上的拦截率和误拒率。

## 当前禁止宣传

- “视觉准确率全面超过 OpenAI 官方原生方案”；
- “比所有视觉 MCP 更快/更准”；
- “Luna 视觉能力必然强于任何旗舰模型”；
- “绝不会产生 API 费用”或“服务端一定按订阅结算”；
- “完全沙箱化”“绝对安全”“100% 防提示注入”；
- “所有 ChatGPT 账号都能使用 Luna”；
- “缓存零延迟”或“缓存让本地处理快 X 倍”；
- 未做同机对照时宣称“比官方节省 X% token/时间”。

## 与官方原生方案的正确对比

官方 Codex 原生图片输入不是弱方案。用户临时看一张图、且 Codex 本身就是主代理时，原生附图通常更直接。

Visual Evidence Gateway 的优势只在特定系统问题上成立：

1. 主代理是 DeepSeek/OpenCode，不想为了少数图片步骤迁移整个任务；
2. 需要路径授权、只读边界和最小上下文返回；
3. 需要结构化证据、图片索引、不确定性和模型身份校验；
4. 需要长图/小图的裁剪分块重试、签名缓存和失败关闭；
5. 需要把“是否真的能通过订阅读取像素”做成安装闸门。

因此首页应写“更适合跨主代理的受控视觉委派”，不要写“原生视觉的全面替代品”。

## 推荐首页文案

英文：

> **Keep your main agent. Add a controlled Luna vision evidence path.**
>
> Visual Evidence Gateway gives DeepSeek, OpenCode, and other text-first agents one read-only tool for pixel-dependent work— with path authorization, adaptive image retries, strict evidence schemas, prompt-injection containment, minimal-context returns, and no silent API-key fallback.

中文：

> **保留你的主代理，只补一条受控的 Luna 视觉证据链。**
>
> Visual Evidence Gateway 让 DeepSeek、OpenCode 等文本代理只在答案依赖像素时调用 Luna，并通过一个只读 MCP 工具统一执行路径授权、自适应裁剪/分块、严格证据 Schema、图片提示注入收敛、最小上下文返回和禁止静默 API 计费降级。

## 发布后最值得继续优化的五项

1. 建立 100–300 张真实开发截图基准，按 OCR、UI、图表、报错、长图和多图比较分层；
2. 做 `Visual Evidence Gateway vs 原生附图 vs OCR vs 薄 MCP` 同机对照，而不是跨账号比较；
3. 对裁剪/分块、缓存、注入终检分别做消融实验，量化它们真正贡献；
4. 在 Windows/macOS/Linux 和 Codex/OpenCode 两类宿主中跑矩阵；
5. 把真实结果自动生成机器可读 JSON，并只由验证脚本更新 README 的“实测结果”区，避免手工夸大或数据漂移。
